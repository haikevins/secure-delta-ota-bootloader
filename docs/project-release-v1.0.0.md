# Project Release v1.0.0

[↑ Documentation Index](README.md) · [← Root README](../README.md) · [Changelog](../CHANGELOG.md)

> **Release type:** stable source/portfolio release of the repository. This is intentionally separate from device firmware releases generated by the protected pipeline, which use identifiers of the form `fw-v<version>`.

## Scope

`v1.0.0` marks the project as a complete end-to-end secure OTA reference implementation for the STM32F103 + ESP32 + external SPI NOR target stack.

The release includes:

- STM32 bootloader/application firmware and recovery state machines;
- ESP32 network gateway and UART OTA bridge;
- authenticated full and delta firmware containers;
- host-side signing, release, inspection, benchmark, and HIL tooling;
- automated build/test/security validation;
- checked-in hardware and benchmark evidence;
- architecture, protocol, security, recovery, and reproduction documentation.

It does not introduce a new OTA protocol or firmware format beyond the behavior already documented in this repository. The purpose of the `v1.0.0` source release is to freeze a reviewed, reproducible project baseline.

## Evidence snapshot

The checked-in benchmark reference records:

- bootloader flash: `11,400 B`;
- application v2 flash: `11,276 B`;
- signed delta SDOT: `1,174 B`;
- signed full SDOT: `11,480 B`;
- signed delta savings: **89.77%**.

The physical HIL suite records **9/9 PASS**, including reset/power-loss behavior during reconstruction, backup, installation and rollback, plus HTTPS truncation, MQTT disconnect, and tampered-signature rejection.

## Reproduce the release baseline

With GNU Arm Embedded GCC installed:

```bash
git diff --check
make warning-check TOOLCHAIN=gcc
make check TOOLCHAIN=gcc
make benchmark TOOLCHAIN=gcc
sha256sum -c SHA256SUMS.txt
```

The supported Clang/LLD fallback is documented in [Toolchain Selection](toolchain-selection.md).

Hardware validation is intentionally separate from host-only CI:

```bash
make hil-test
```

Use the documented HIL setup and safety preconditions before running physical fault injection.

## Security posture

The repository ships without production private signing keys and with the target trust anchor intentionally unprovisioned. `v1.0.0` therefore demonstrates the security architecture and release flow without pretending that repository test material is production key custody.

The project does not claim protection against invasive physical attacks, compromise of the signing environment, denial of service, firmware confidentiality, secure-element storage, irreversible production debug locking, or fleet-scale rollout management.

See the [Threat Model](threat-model.md) and [Security Policy](../SECURITY.md).

## Source release versus firmware release

The repository tag:

```text
v1.0.0
```

identifies this source/portfolio baseline.

The protected firmware-release workflow publishes device artifacts under identifiers such as:

```text
fw-v2
fw-v3
...
```

Those firmware releases carry application build versions, signed SDOT artifacts, manifests, hashes, and release notes. They should not be renamed to semantic source tags because the bootloader's anti-downgrade policy depends on monotonic firmware version values.

## Publication notes

For the GitHub `v1.0.0` release:

- tag the reviewed merge commit on `main`;
- use this document as the release-note basis;
- rely on GitHub's source archive for the repository release;
- do not attach production signing keys or credentials;
- publish device firmware artifacts through the protected `Firmware Release` workflow instead of attaching ad-hoc unsigned binaries to the source release.
